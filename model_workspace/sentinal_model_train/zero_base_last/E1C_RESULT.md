## 0.1 勘误（本文件最初版本有两处目标函数错误，以此节为准）

### 错误 1：第二轴用了 `weight_bytes`，但计划里应该是 cycle

实际跑的目标是：

```
DEFAULT_OBJECTIVES = ["bytes", "fpr_val"]
```

`cycle` **从未进入目标函数**，被 `macs` / `proc_passes` 顶掉了。而 MAX78000 的权重预算
约 442 KB，本模型只占 1.5%~18% —— **内存从来不是瓶颈**，所以 bytes 是个弱轴。

### 错误 2：`proc_passes = Σceil(in/64)` 不能代表 cycle，撤回「9 → 7 = −22%」

`izer/backend/max7800x.py:454,460` 同时定义了：

```python
out_expand[ll] = (output_chan[ll] + MAX_PROC-1) // MAX_PROC   # ceil(out/64)
in_expand[ll]  = (input_chan[ll]  + MAX_PROC-1) // MAX_PROC   # ceil(in/64)
```

`in_expand` 把输入通道分成若干趟，每趟只处理 1/in_expand 的输入，**总工作量不变**，
所以它在 cycle 总量里约掉。进 cycle 的一阶模型是：

```
cycles ≈ Σ_l  ceil(out_l / 64) · in_l · k_l · T_l
```

（**这是推导值，没有 ai8xize 实测背书**；真实的 cycle 估算器在 `izer/cycles.py`，
本文件没有读过它，也没有跑过。方向可信，绝对值不可信。）

按此模型：基线 **118,272**；t49（12 KB）**37,376（−68.4%）**；t7（6.5 KB）**31,104（−73.7%）**。
注意这比原先写的 −22% 强得多，但也同样未经实测。

### 错误 3：精度轴用错了指标（这条最要命）

| 指标对 | pearson | R² | mean(val−test) | sd(差) |
|---|---|---|---|---|
| **AUC** | 0.767 | **0.588** | **+0.0002** | **0.0008** |
| FPR@TPR95 | 0.641 | 0.411 | **+0.0030** | 0.0045 |
| TPR@FPR1% | 0.751 | 0.564 | −0.0156 | 0.0172 |

AUC 的 val/test 偏差几乎为 0（sd 比 FPR 紧 5.6 倍）。**AUC 一直在 CSV 里，但没参与选择。**
所以问题不是「val 作为搜索目标偏弱」，而是「把高方差、有 +0.003 系统偏差的
FPR@TPR95 当了目标」。§3.1 的措辞应以此节更正。

**结构性事实：cycle 轴在剪枝区是平台。** 12 KB → 6.5 KB（权重再砍 46%）只换来

把输出通道压到 64 以下之后就没有并行度可捡了。

**所以 t49 的结论不变，但理由换了**：它是 cycle 轴与精度轴共同的拐点，
不是"字节省得最多"的那个点。

## 2. 搜索设置

| 项 | 值 |
|---|---|
| 目标 | `minimize(weight_bytes)`, `minimize(fpr_val)` 双目标 |
| 搜索空间 | conv1 [16,64] / conv2 [24,96] / conv3 [24,96] / conv4 [16,64] / conv5 [8,32] / conv6 [4,16]，步长 4 |
| 空间依据 | E1b 单层敏感度（单层 75% 全免费 → 区间一律放到 75% 档） |
| 采样器 | TPESampler(multivariate, n_startup_trials=12)，8 个 E1b 已测点热身 |
| 微调 | Adam lr=1e-3, wd=1e-4, 5 epoch, CrossEntropy（与 E1b 同配方） |
| 设备 | CUDA（RTX 5070 Ti Laptop），112 s/trial |
| trials | 60（全部 complete，0 失败） |

搜索空间里最重要的数字是 **conv3 的输入 = conv2 的输出**：MAX78000 只有 64 个并行
卷积处理器，输入通道 >64 要多走一遍。基线是 2+1+2+2+1+1 = 9 趟；只要 conv2 ≤ 64，
conv3 立刻省一趟 → **最少 7 趟**（conv1 的输入是 128，动不了）。

## 3. 复核：为什么不能直接信 Optuna 的排序

### 3.1 val 作为搜索目标偏弱

对 60 个 trial 统计 val 与 test 的 FPR：

```
pearson 0.641    spearman 0.684    (R² ≈ 0.41)
mean(val − test) = +0.0030    sd = 0.0045    最大差 0.018
```

**val 只解释了 41% 的 test 方差。** 所以 val 前沿上的排序有相当一部分是噪声顺序 ——
不能直接当答案。

### 3.2 5 个 epoch 的微调本身不带来增益

trial 0 = **不剪枝** + 5 epoch 微调：test 0.0116，与基线 0.0118 持平；
3 seed 复核后 test 均值 0.0113（基线 0.0118），val 0.0138（基线 0.0103）。

结论：微调的作用是**恢复剪枝损伤**，不是提升模型。E1b 里那些"负 dFPR"确实是噪声。
（所以「换个更大的微调预算就能更好」这个假设不成立 —— 这也是我没有把时间花在
`--polish-epochs` 上的原因。）

### 3.3 复核方式

对 9 个候选各跑 **3 个独立的 seed**（1001/1002/1003），报 test 的 mean 与
[min,max]。seed 噪声由此压低到 ~0.001，两点差距 ≥0.002 才算真差异。

## 5. 推荐

### 主推：t49 `24/32/32/24/16/8` —— 12,048 B

| 指标 | 值 | vs 基线 |
|---|---|---|
| 权重 | **12,048 B** | **−84.8%** |
| MACs | 997,392 | **−83.3%** |
| proc_passes | **7** | 9 → 7（−22%） |
| test FPR@TPR95 | 0.0138（3 seed 均值） | +0.0020 |
| test TPR@FPR1% | 0.9424 | **+0.0036（更好）** |
| test AUC | 0.9956 | −0.0006 |
| test Top1 | 97.37% | −0.22 pp |

**FPR 与 TPR@FPR1% 两个方向都不输基线**，代价只有 AUC −0.0006 和 Top1 −0.22pp。
`t58`（11,992 B）与它并列 FPR，但 MAC 多 9%，所以选 t49。

### 保守：t5 `48/48/24/48/16/16` —— 22,560 B

FPR 0.0108、TPR@FPR1% 0.9478，**两个指标都比原模型好**（在 1σ 内，不能算真提升）。
权重仍省 71.6%、MAC 省 65.2%、趟数 9→7。如果你要的是"绝不比现在差"，选这个。

### 极限：t7 `16/24/24/16/8/4` —— 6,504 B

−91.8% 权重、−90.5% MAC，代价是 FPR 从 1.18% 涨到 2.48%（**约 2 倍**）、
TPR@FPR1% 掉到 0.892。适合"板子上真的放不下"的场景，不适合做交付配置。

## 5.5 补充实验：微调配方本身也是瓶颈

§3.2 发现 lr=1e-3 + 5 epoch 对满通道模型略微有害，那就可疑：**前沿的绝对数值可能被配方
压低了，而不是被剪枝压低的。** 对最激进的 2 个配置换配方重跑（2 seed）：

| 配置 | bytes | lr 1e-3 / 5 ep | **lr 3e-4 / 12 ep** | 变化 |
|---|---|---|---|---|
| t7 `16/24/24/16/8/4` | 6,504 | 0.0248 | **0.0215** | **−0.0033** |
| t46 `20/24/28/20/12/8` | 8,528 | 0.0181 | **0.0151** | **−0.0030** |

两个配置、同一方向、同样约 −0.003，而且 seed 间离散度从 0.0030 收到 0.0018。

**结论：主表里所有数字都是"在 lr=1e-3 / 5ep 这个偏激进的配方下"的成绩，偏保守（悲观）。**
换成 lr=3e-4 / 12ep，激进端大约还能白拿 0.3 个百分点。也就是说：

- 6.5 KB 的真实水平更接近 **2.15%** FPR，不是 2.48%
- 8.5 KB 更接近 **1.51%**，不是 1.81%
- 12 KB 拐点大概率还能再往左（更省内存）挪一格，但这一格没有实测

代价：12 epoch 使单 trial 从 110 s 涨到 198 s（1.8×）。用新配方重跑 60 trials 约需 3.5 h，
本次时间窗不够，留作下一步。

## 6. 必须说清楚的三个不确定性

1. **test 被用于复核选点**，所以上表的 test 数字对入选者略偏乐观。
   完全无偏的估计只有 val 那一列，但 val 噪声大（sd 0.003~0.007）。
   真实性能大概落在两者之间。
2. **val 与 test 存在 +0.0030 ± 0.0045 的系统性差**（同一个模型，val 读出更高 FPR）。
   这说明两个 split 的正负样本构成不完全同分布，FPR@TPR95 这个指标对两侧分布都敏感。
   绝对数值不要精确到 0.001 去比。
3. **没有测真实 cycle**。`proc_passes` 只是基于"输入通道 >64 就要多走一趟"的代理，
   依据是 ai8x-synthesis `izer/load.py:106` 与 `:260`。真 cycle 要对前沿那几个点跑
   ai8xize 才能确定 —— 前沿只有 5~6 个点，成本可控。
